# 프론트 성능 개선 결과

## 범위

`develop`의 `65c9f98`을 기준으로 `perf/frontend-loading` 브랜치에서 작업했다. P01~P09를 구현했고, 사용자의 후속 요청에 따라 서버 P10은 제외했다. 첨부한 노란색 사용자 이미지를 공통 기본 프로필로 교체했다. 변경은 목적별 로컬 커밋이며 푸시·PR 생성·배포는 수행하지 않았다.

## 성능 측정

| 화면 | 주요 텍스트 준비(초) 전 → 후 | 관측 LCP(초) 전 → 후 | gzip JS(KB) 전 → 후 | API 요청 전 → 후 |
| --- | ---: | ---: | ---: | ---: |
| 타자 메인 | 6.61 → 1.89 | 6.62 → 1.89 | 1091.8 → 167.8 | 5 → 4 |
| 일상 타자 | 6.73 → 2.02 | 6.73 → 2.03 | 1091.8 → 163.7 | 5 → 4 |
| 커뮤니티 목록 | 2.25 → 2.26 | 2.25 → 2.26 | 166.8 → 169.4 | 5 → 3 |
| 일반 게시글·댓글 50개 | 4.37 → 4.32 | 2.83 → 2.80 | 299.8 → 301.0 | 57 → 55 |
| 굵은 글씨 게시글 | 5.13 → 2.83 | 5.13 → 2.82 | 576.6 → 301.0 | 57 → 55 |
| 게시글 작성 | 3.61 → 3.60 | 3.60 → 3.59 | 463.9 → 466.5 | 3 → 2 |
| 멘토링 방 10개 | 3.54 → 3.56 | 3.54 → 3.56 | 228.7 → 231.2 | 39 → 38 |
| 로그인 | 1.55 → 1.60 | 1.56 → 1.60 | 166.7 → 171.6 | 0 → 0 |
| 코드 타자 | 6.59 → 6.64 | 6.85 → 7.00 | 1100.9 → 1183.7 | 4 → 3 |
| 모바일 로그인 | 1.55 → 1.60 | 1.56 → 1.60 | 166.7 → 171.6 | 0 → 0 |

타자 메인·일상은 모든 표본에서 gzip JS 250KB 이하·준비 시간 3초 이하를 충족했다. 기본 서식 게시글은 BlockNote fallback 요청 없이 gzip JS 301KB로 310KB 목표를 충족했다. 주요 이미지 3종은 438,296 bytes로 450KB 목표를 충족했고, 모바일 hero HTTP 요청과 API host의 빌드 자산 요청은 0회였다. 인증 화면을 제외한 각 cold 진입의 `/me`는 1회였다. 30개 페이지 표본 모두 준비 성공, 처리되지 않은 page error·미지원 fixture API 0건, 관측 CLS 0.1 이하였다.

코드 타자의 JS는 정상 Worker 제공 등의 비용으로 늘었고 준비 시간도 줄지 않았다. 로그인·목록·작성·멘토링의 시간은 대체로 비슷한 범위이며 모든 화면이 빨라졌다고 해석하지 않는다. 일반 게시글과 굵은 글씨 게시글은 ready 대상이 각각 마지막 댓글과 본문으로 다르다.

조건: Chrome 156.0.8078.73, 프로덕션 빌드, 각 화면 3회 cold 진입의 중앙값. CPU 4배 slowdown, 지연 150ms, 다운로드 200,000 bytes/s, 업로드 93,750 bytes/s. 기본 viewport 1440×900, 모바일 로그인 390×844. API는 50ms 지연의 로컬 fixture이며 운영 서버에 연결하지 않았다. 댓글 50개·멘토링 방 10개·메시지 1,000개 조건을 유지했다.

기준 소스는 `65c9f98e3f156063f11292dc13bb5739e74dfe63`, 최종 제품 소스 트리(`HEAD:src`)는 `a3af5ad919ead3470f813e6de4fa6a9073ea5dfb`이다. 중단된 측정과 수정 전 취소 오류 표본은 별도로 보존하고 최종 집계에서 제외했다.

페이지 진입 후 약 10초 동안 관측했다. 준비 시간은 주요 텍스트의 출현 시점이다. LCP·CLS는 이 관측 구간의 로컬 측정이며 현장 p75 지표가 아니다. JS 용량은 관측 구간에 완료된 페이지 resource timing의 합계이며, 특히 코드 화면의 늦게 완료되는 Worker 다운로드까지 모두 합한 총량은 아니다.

## 검증

- `npm run lint`: 통과.
- `npm run build`: TypeScript 및 프로덕션 빌드 통과.
- `npm run test:performance`: 25개 통과. 모바일 breakpoint, 청크 실패 후 실제 새로고침 복구, 기본·미지원 서식, Worker·코드 입력·언어 전환, 프로필 조회·재발급·계정 전환 경합, 문제 응답 지연·이미지 지연·실패 검증.
- `npm run test:community`: 66개 통과. 기존 댓글 아바타·파일 첨부·GIF·목록 복원·캐시·낙관적 갱신·타자 캐시 회귀 검증.
- 일반 headed Chrome 153.0.8010.12의 독립 CDP 세션에서 실제 `document.hidden === true` 확인. 통계 요청은 표시 중 1회, 숨김 5.5초 후에도 1회, 복귀 후 2회였다. Playwright의 visibility 제어 회귀 테스트와 별도로 수행했다.
- 홈·멘토링 이미지 요청을 각각 5.2초 보류한 뒤 실패시켜도 이름이 먼저 표시됐다. 이미지 지연·실패 구간의 관측 CLS는 둘 다 0이며 해당 카드/아바타의 위치·크기도 유지됐다.
- 새 기본 프로필 PNG와 WebP는 RGBA 픽셀과 크기가 일치한다.

## 조건부 후속 항목 평가

- 병아리 animated WebP는 기존 180프레임과 움직임을 유지했다. 전체 프레임·위치·타이밍을 유지한 q80 재압축 샘플은 큰 버전 2,686,564 → 2,612,394 bytes(약 2.8%), 작은 버전 598,694 → 574,266 bytes(약 4.1%)였다. 절감이 작아 추가 손실 압축은 적용하지 않았다. 15fps 샘플은 더 작지만 기존 움직임의 빈도가 달라지므로 채택하지 않았다.
- 글자 수 계산은 이번 구현 범위에서 유지했다. baseline의 1/20/60문단(최대 약 15,700자) 입력에서 관측 지연 최대 40ms, 50ms 초과 long task 0회였다. 최종 소스에서도 각 1회 재측정하여 최대 40/32/40ms, long task 0회를 확인했다. 최종 입력 집계는 실제 입력 시작 이전의 클릭·문서 끝 이동 이벤트를 시각 기준으로 제외했으며 100ms 목표를 충족했다. 한글 IME·대형 표 등으로 일반화하지 않는다.
- 마이페이지의 추가 모달 분리, 전역 memo/가상화, 공격적인 prefetch, query 취소 정책 변경은 이번에 적용하지 않았다. 현재 측정에서 핵심 병목으로 입증되지 않았거나 기존 캐시·표현 동작에 추가 영향을 주는 항목이다.

## 남아 있는 경계

- 코드 타자에서 사용하는 Monaco 본체와 Worker, 미지원 본문의 BlockNote fallback에는 큰 청크가 남는다. 기능 제거·경고 임계값 조정으로 수치를 숨기지 않았다.
- 댓글별 전체 답글 수 요청, 방별 역할 멤버 요청, 전체 메시지 폴링은 제외된 P10의 서버 계약에 의존하므로 유지했다.
- 실제 서버 응답 시간·CDN·배포 캐시·현장 사용자 Core Web Vitals는 측정하지 않았다. 로그인은 Turnstile 키 없는 안내 화면 조건이며 실제 인증 제출 성능은 포함하지 않는다.
- 큰 Monaco 청크에 대한 Vite 경고는 남아 있다. 코드를 실제로 사용하는 화면까지 같은 용량 목표로 줄였다는 의미는 아니다.
- 이전 전체 회귀 실행에서 파일 드롭 테스트 1개가 일시 실패했으나 독립 재실행 및 최종 전체 66개 실행에서 통과했다. 제품의 글쓰기 흐름을 해당 실패 때문에 수정하지 않았다.

## 재현

```sh
npm ci
npx playwright install chromium
npm run lint
npm run build
npm run test:performance
npm run test:community
```

두 테스트 명령은 4173 포트를 사용하므로 순차 실행한다. 프로덕션 테스트는 API를 fixture로 대체한다. 실행 시간은 성능 점수로 사용하지 않는다. 테스트 범위와 조건은 `tests/performance/README.md`를 참고한다.

성능 원시 로그, baseline/final manifest, 반복 측정 스크립트와 스크린샷은 작업 당시 로컬 산출물 `switch-performance-audit-2026-10-28` 폴더에 별도로 보관했다. 제품 번들·커밋에는 포함하지 않았다.
