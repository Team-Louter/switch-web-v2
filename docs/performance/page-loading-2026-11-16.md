## 측정 조건과 지표

- Vite **프로덕션 빌드**, HTTP/1.1 + gzip. 시나리오마다 새 브라우저 context와 빈 캐시, 각각 **5회 중앙값**.

- LCP·CLS와 Event Timing은 실험실 관측값이다. 실제 사용자 p75 INP 또는 Core Web Vitals 통과를 주장하지 않는다. SPA 전환 시나리오의 LCP는 첫 목록 문서에 속하므로 전환 LCP로 사용하지 않는다.
- 원시 표본 요약과 빌드 manifest SHA-256: [JSON](./page-loading-2026-11-16.json). 개선율 = `(변경 전 - 변경 후) / 변경 전 × 100`.

## 반복별 병목·변경·검증

### 1. 페이지 청크와 프로필 요청의 직렬 대기 해소

원인: 최상위 Suspense 하나가 지연 페이지와 AppLayout을 함께 감싸 페이지 청크가 끝나기 전까지 레이아웃의 프로필 조회가 시작되지 않았다.

- 기존 AsyncBoundary를 페이지 Outlet에 적용해 레이아웃을 먼저 마운트하고 청크와 프로필 조회를 병렬화했다. 로딩·실패 표시는 기존 공용 UI를 사용한다.
- 홈 준비 **2,621.0 → 2,444.1ms (6.7%)**, 상세 준비 **4,344.9 → 4,185.5ms (3.7%)**.
- 유지 결정: 데이터 준비 시간도 줄었으며 단순 로딩 표시 변경으로만 얻은 수치가 아니다.
- 검증: 청크를 차단한 동안 `/me` 시작, 중복 조회 없음, 청크 실패 시 메뉴 유지 및 다른 페이지 이동.
- 구현 커밋 `5c6ea33`, 테스트 `1f188bc`.

### 2. 답글 없는 댓글의 추가 API 요청 제거

원인: 댓글마다 `/total-reply-count`를 호출해 50개 댓글에서 50개 요청이 추가됐다. 제한된 연결 수 때문에 뒤쪽 요청은 대기 시간이 누적됐다.

- 수정: `src/entities/community/model/postQueries.ts`.
- `replyCount === 0`일 때만 전체 답글 수 조회를 생략한다. 양수 또는 누락이면 기존 조회와 실패 fallback을 유지한다.
- 상세 준비 **4,185.5 → 2,695.9ms (35.6%)**, 준비 전 API **54 → 4개 (92.6%)**, 전체 답글 수 API **50 → 0개 (100%)**.
- 서버 계약 확인: `switch-server` 커밋 `f1ee586b2e966373bf482ca8819430a1b159cbd9`의 `CommentServiceImpl`과 `CommentRepository`는 삭제 표시된 자식도 직접 자식 수에 포함한다. 직접 자식이 0이면 하위 답글도 0이다. 양수일 때는 중첩 답글 전체 수를 위해 기존 요청이 필요하다.
- 검증: 0·양수·누락·삭제된 부모·API 실패와 알림 진입 후 답글 갱신. fixture도 직접 자식 수 계약에 맞췄다.

단일 API가 빨라진 것은 아니다. 최종 상세 표본에서 게시글 API는 **163.0 → 160.8ms**, 댓글 목록은 **157.4 → 162.2ms**였다. 프로필은 청크와 대역폭을 공유하면서 **159.0 → 472.1ms**로 늘었지만 더 일찍 시작해 전체 준비는 단축됐다. 요청별 지연과 화면 전체 대기는 구분해야 한다.

### 3. 댓글 입력 시 변경 없는 본문·댓글 렌더링 재사용

원인: 댓글 초안 한 글자마다 Markdown 본문과 기존 댓글 50개가 다시 렌더링됐다.

- 수정: `src/pages/community/ui/CommunityDetailPage.tsx`, `CommunityCommentBranch.tsx`, `CommunityPostBlockContent.tsx`.
- 본문 JSX·댓글 하위 목록을 메모화하고 자식에 전달하는 콜백·집합 참조를 안정화했다. 변경된 댓글·파일·현재 사용자 등은 기존 의존성을 따라 갱신한다.
- 댓글 20자 입력 ScriptDuration **544.6 → 54.1ms (90.1%)**. 상세 준비 **2,695.9 → 2,663.6ms (1.2%)**는 부차적인 작은 차이다.
- 별도 진단 빌드에서 댓글 컴포넌트 함수 진입을 직접 계수: 변경 전 `[1000, 1000, 1000]`, 최종 `[0, 0, 0]`. 입력 전 포커스 렌더를 제외한 20자 입력 구간이며 초기 50개 댓글은 정상 표시된다. 이 계측 빌드의 시간은 성능 표에 섞지 않았다.
- React Fiber flags를 읽은 탐색용 `renders` 값은 실제 함수 실행 횟수로 해석하지 않았다.
- 검토 중 상대 시간 갱신이 메모화로 멈출 수 있음을 발견해 표시값이 바뀌면 댓글을 다시 렌더링하도록 보완했다. 해당 동작을 테스트했다.
- 입력·등록·수정·삭제·답글·낙관적 표시·첨부파일·알림·스크롤 복원 회귀 테스트를 수행했다.

## 남은 비용과 종료 판단

1. **운영 API·CDN**: 이 변경은 서버 처리 시간이나 CDN 전달 경로를 바꾸지 않는다. 기존 이슈의 운영 수치는 네트워크·API 환경이 다르므로 이 표와 직접 비교하지 않는다. 서버 CPU·DB·연결 풀 중 어느 것이 원인인지는 운영 지표 없이 확정할 수 없다. 운영 인프라 조사는 #148에 남긴다.
2. **작성 화면의 필수 에디터**: 느린 네트워크의 최초 준비는 여전히 3,470ms다. 전체 JS encoded 전송량은 목록 168,056 → 168,974B, 상세 297,719 → 298,448B, 작성 462,928 → 463,350B다. 번들 축소를 달성했다고 주장하지 않는다. 기능 유지 조건에서 에디터 교체나 직렬화 변경은 별도 검증이 필요한 큰 변경이다.
3. **작성 중 연산**: 60문단을 붙여넣고 20자 입력한 추가 실험(동일 CPU 4배, 5회)에서 누적 JS 중앙값 159ms, 최대 이벤트 `[48,24,24,24,24]ms`, 입력 중 long task 0건이었다. 글자 수 제한·서식 처리 의미를 바꾸는 최적화는 적용하지 않았다.
4. **답글이 실제 존재하는 댓글**: 전체 하위 답글 수 조회는 유지한다. 이를 합치려면 서버 응답 계약 또는 배치 API가 필요하다. 카운트 표시를 누락하거나 지연시켜 속도를 높이지 않았다.
5. **이미지·분석 리소스**: 이 fixture에는 본문 이미지가 없다. 이미지가 많은 실제 게시글과 외부 분석 요청을 포함한 운영 CWV는 배포 후 별도 측정해야 한다. 기존 이미지·아바타·GIF·첨부파일 기능은 회귀 테스트로 확인했으며, 측정 근거 없는 이미지 정책 변경은 하지 않았다.

네 단계의 효과를 최종 빌드에서 재확인했다. 작은 차이는 성과로 확대하지 않았다. 남은 초 단위 비용을 프론트에서 더 줄이려면 필수 에디터·API 계약·인프라까지 범위가 넓어지고 기능 안정성 위험이 커져 이번 반복은 여기서 종료한다.

## 재현

[serve-fixture.py](../../scripts/performance/serve-fixture.py)는 로컬 전용 읽기 API와 빌드를 제공한다. [measure-pages.js](../../scripts/performance/measure-pages.js)는 위 조건의 5회 측정 함수다.

```sh
VITE_API_BASE_URL=http://127.0.0.1:4173/api npm run build -- --manifest
PERF_DIST="$PWD/dist" python3 scripts/performance/serve-fixture.py
```

별도 터미널에서:

```sh
npx --yes --package @playwright/cli@0.1.24 playwright-cli --session switch-perf open about:blank
sed 's/SCENARIO/nav-detail/g' scripts/performance/measure-pages.js > /tmp/switch-perf-measure.js
npx --yes --package @playwright/cli@0.1.24 playwright-cli --session switch-perf run-code --filename /tmp/switch-perf-measure.js
```

`SCENARIO`: `list`, `home`, `input`, `write`, `nav-detail`, `nav-write`. 반환 JSON의 `ready`, `lcp`, `cls`, `resources`, `input.metrics`를 사용한다. `ScriptDuration`은 초이므로 1,000을 곱한다. 단독 렌더링 시간은 별도 분리하지 않았으며 ScriptDuration에는 입력 관련 앱 로직도 포함된다. `renders`는 탐색용이므로 성과 산정에서 제외한다.

보조 실험은 CPU rate를 1, network latency를 0, download/upload throughput을 -1로 바꾼다. baseline과 최종 빌드를 각각 같은 서버 설정으로 실행하고 브라우저·다른 측정 작업을 동시에 실행하지 않는다. 운영 API 지연 재현이 필요하면 별도의 실험으로 기록하며 fixture 결과와 혼합하지 않는다.
